## 절차

### 1. 히스토리 로드 — 중복부터 막는다

```bash
cat "/Users/kakao/Documents/2. 개인/Walter Project/01_자동화/이슈_히스토리_테크.json"
```
`{"date", "category", "title"}` 배열이다. **이미 다룬 주제는 제외.** 단 **새 국면**(출시 예고 → 실제 출시, 루머 → 공식 발표, 스펙 공개 → 실사용 리뷰)은 후보로 살리고 무엇이 새로운지 명시한다.

테크는 같은 제품이 단계별로 계속 뉴스가 되므로 이 구분이 특히 중요하다.

### 2. 카테고리별 이슈 수집 [웹검색]

각 카테고리마다 **최근 1~2주** 이슈를 찾는다. 테크는 주기가 짧으니 경제보다 창을 좁게 본다.

수집 기준:
- **확정된 사실** — 출시일·가격·스펙이 공식 발표됐나
- **독자가 결정해야 하는 것** — 살까 말까, 업그레이드할까, 갈아탈까
- **검색이 몰리는 시점** — 언팩·신제품 공개·대형 업데이트 전후

버릴 것: 출처 불명 루머, 벤치마크 유출만 있는 건, 광고성 리뷰 기사.

> ⚠️ 테크는 루머와 확정이 섞여 돈다. **공식 발표인지 업계 관측인지 반드시 구분**해 표기한다. 불확실하면 "확인 필요".

### 3. 브리핑 출력

```
📋 테크 이슈 브리핑 — YYYY-MM-DD

[AI·LLM 모델]
1. <제목> — <한 줄 요약> (출처: <매체>, <날짜>) [공식/관측]
2. ...

[반도체·파운드리]
...
```

### 4. 추천 TOP 3

검색량·시의성·경쟁도·독자 관심도를 종합해 3개를 고르고 이유를 한 줄씩 적는다.

### 5. 🥊 악마의 변호인 검증 ★필수

**TOP 3를 그대로 확정하지 않는다.** 각 후보를 스스로 공격해 살아남은 것만 통과시킨다. 목적은 **헛글 방지**.

| # | 질문 | 확인할 것 |
|---|---|---|
| ① | **안 먹힐 이유는?** | 실제 검색 수요가 있나. 관심층이 너무 좁지 않나. 이미 다 아는 내용 아닌가 |
| ② | **경쟁 포화도는?** | IT 전문 매체가 이미 도배했나. 유튜브 리뷰가 검색을 먹고 있지 않나. 내가 더할 게 있나 |
| ③ | **더 나은 앵글은?** | 스펙 나열 대신 비교·선택 기준으로 바꿀 수 없나. 대상을 좁히면(예: 전체 → 기존 사용자 업그레이드 판단) 살아나나 |

```
🥊 악마의 변호인

후보 1: <제목>
 ① 안 먹힐 이유 — ...
 ② 경쟁 포화도 — ...
 ③ 더 나은 앵글 — ...
 → 판정: 통과 / 앵글 수정 후 통과 / 탈락
```

**셋 다 탈락하면 억지로 살리지 말고** 2단계로 돌아가 다른 카테고리에서 다시 고른다.

### 6. 최종 확정

통과분만 남긴다. 앵글이 수정됐으면 수정된 앵글로 적는다.

### 7. 히스토리 append

```json
{"date": "YYYY-MM-DD", "category": "<카테고리>", "title": "<제목>"}
```
**기존 항목은 건드리지 않고** 배열 끝에 덧붙인다.
